# brain-prd — 条件对齐 + 立卷 PRD（功能/需求验收基线）

> **来源**：[[视频方法论对照与开发流程优化-设计提案]] §3.1 / §4(B)，Doctor 2026-06-13 裁定建独立 skill。**十轮合同（2026-08-18）**：PRD 是功能/需求验收基线、不是审批单——任务已授权且方向明确时直接立卷实施，不再加一轮 PRD 文本审批；对齐改为**条件触发**（模糊/信息不足/范围冲突/验收标准落不成时按需问清）。
> **两段价值**：① **对齐**（按需）——发现需求模糊、信息不足、范围冲突或验收标准无法落成时，用 §5 问题库问清，不靠 CC 猜；Doctor 原始指令已把目标、范围和验收说清时跳过。② **起草**——把「做成什么样算完成」写成功能/需求验收基线。
> **不改 G-X4 任何治理铁律**：PRD checkbox 实施者只填三态、`[✓]` 由 Doctor 或 Doctor 明确指定且未参与实施的独立验收方落、双向闭环关闭、沙箱禁 git 一律照旧。

---

## §1 · 何时用（When）

**用**：
- 显式：`/prd`、`/prd [任务简称]`、"立PRD"、"起草PRD"、"写交付标准"、"写个 go"。
- 主动：任务已获执行授权 + 存在功能或明确非功能需求 + 达复杂度阈值（多文件改 / 跨小时 / 跨项目 / 凌晨自主）→ **直接立卷**（不主动问「是否同意立 PRD」）；Doctor 明示「本任务不用立 PRD」时覆盖。

**不用**（避免官僚化）：单一问答 / 解释 / 研究讨论；单文件小改（< 10 处）；**无功能交付的事务**——纯清洗/去重/迁移/归档等事实核验类**不立 PRD，仍按既有授权工作流执行**（仅原本属于客观普通 TODO 的事项适用 G-X136 常驻授权代勾）。**规模（多文件/跨小时）只是必要条件，「有功能可验收」才是立 PRD 的判据**（2026-08-15 Doctor 立 · 回归「功能验收」初衷）。

---

## §2 · 什么算合格（Done · 可复核）

1. **对齐按需**：核心需求 / 开发方向 / 交付验收 三维——Doctor 原始指令已说清时**跳过对齐**；发现模糊/信息不足/范围冲突/验收标准无法落成时用 §5 问清（见 §4 Step 2）。
2. **文件已落**：`~/Documents/Claude/brain/logs/checkpoints/{YYYY-MM-DD}_{任务简称}_PRD.md` 存在（`ls` 可见），从 `templates/prd-acceptance-template.md` 复制填成。
3. **§一 目标**：含动机 + 范围 + **Doctor 原始指令逐字引用** + 规模估算；frontmatter 填 `task_authorization`（state/source_type/source_ref/quote/scope）、`roles`（implementers / independent_reviewers）、`acceptance_authority`（authority/designation_source_ref/designation_quote/designated_at——独立验收方必须能证明「由 Doctor 明确指定且未参与实施」，不能只写一个名字）、`open_decisions`。授权原话找不到时写「授权来源待补」，不得推断或编造；新任务授权无法核实时停在 draft。
4. **§二 交付标准主体＝功能/需求**：验收主体是**用户可感知的行为/结果**（功能需求区）或**性能/安全/可靠性/兼容性/数据质量**（非功能需求区——文件、路径、Grep、`/save` 不算非功能需求）；每项带 `requirement_id → 预期行为/结果 → 验收方法 → 证据 → 状态`，**每项可复核**（机器比对或预先定义的人工验收方法）；§二全留 `[ ]`（起草阶段不填三态）。**Grep 自检：§二 内无"做好了/完整/修复了/优化了"等主观词。**
5. **§2.5 执行清单**：文件/Grep/hash//save/git/self-audit 等过程项在此跟踪，用**无 checkbox 表格**（task_id | task_status | evidence），**不用 PRD 验收四态、不参与功能交付关闭判定**。
6. **§三 非交付项**：写明本任务不含什么（用对齐时划定的边界）。
7. **原则轨只收开发完成后首现的验收裁定**（2026-08-15 Doctor 立）：开发中 Doctor 已拍板的分叉裁定不重复列原则轨——变更记录留痕（时间/方式/结论）即止，验收环节不再重裁一遍。

## §3 · 什么红线（Never）

- ⛔ **需求不落不硬立**：功能或非功能需求无法落成验收标准（"到底要解决什么问题""怎么算验收"有硬缺口）时，**不许**硬立——按需对齐或把缺口记入 `open_decisions`。
- ⛔ **禁阿谀奉承**（毒舌纪律）：不附和、不夸"好主意"、不顺着含糊需求往下滑。答案模糊 / 自相矛盾 / 范围膨胀 → **当场指出 + 要明确**。但毒舌＝较真，不是无礼，守 [[Doctor协作偏好]] 的简洁与尊重。
- ⛔ **不一次轰炸**：一次聚焦一个维度 / 1–2 个问题，优先选择题，别甩一长串问卷。
- ⛔ **实施者不打 `[✓]`**：PRD 内任何 checkbox（无论客观或判断性）`[✓]` 只由 Doctor 或 Doctor 明确指定、且未参与实施的独立验收方落（实施者身份看本轮角色、不看模型身份）。起草阶段 §二 全留 `[ ]`。看到自己将打 `[✓]` → 立即停。**客观 TODO 证据代勾为常驻授权、仅限 PRD 外的普通 TODO**（G-X136 十轮补钉）——「客观」不是自签 PRD 的后门。
- ⛔ **不自动关闭**：只"全 ✓（Doctor 或指定独立验收方落）"或"Doctor 显式取消"两条合法路径；不得 commit 即关 / 标完 Task 即关 / "我觉得完了"即关。
- ⛔ **交付标准不许主观陈述**：不可复核 = 等于没写（G-X4「验收主体＝功能/需求，证据≠标准」）。
- ⛔ **不在沙箱跑 git 写命令**（G-X2）：落盘走 Write；要 commit 贴命令给 Doctor。
- ⛔ **PRD 不授予任务权限，也不撤销已有任务权限**：任务尚未授权时，写出 PRD 不等于获准实施；任务已经授权时，建立 PRD 不得再制造一轮文本审批门。

## §4 · 执行步骤

### Step 1 · 判定要不要立
按 §1。任务已获执行授权且无阻断性歧义 → 直接立卷（不问「是否同意立 PRD」）；授权无法核实 → 停在 draft 先核实授权；Doctor 明示「不用立 PRD」→ 不立 PRD，仍按既有授权工作流执行（仅原本属于客观普通 TODO 的事项适用 G-X136 常驻授权代勾）。

### Step 2 · 条件对齐（按需 · 非每份必做）

**触发条件**（满足其一才启用，Doctor 原始指令已把目标、范围和验收说清时跳过）：需求模糊、信息不足、范围冲突、验收标准无法落成。目标：把"模糊想法"逼问成"清晰可起草的需求"。流程四小步：

**2a · 先复述理解，校准方向**
CC 用"在场"优势，先一句话复述对任务的理解（要解决什么、大概怎么做），交 Doctor **确认或纠偏**——避免后续提问无的放矢。

**2b · 分轮提问（三维度 · 用 §5 问题库）**
按"核心需求 → 开发方向 → 交付验收"顺序，**一次聚焦一个维度、1–2 个问题**，**优先用 AskUserQuestion 工具出选择题**（带推荐项 + trade-off 说明），关键处配简答。一维问清再进下一维；Doctor 答"这维没疑问/你定"即可跳过该维细问。

**2c · 毒舌纪律（边问边卡）**
对照 §5 的「打回信号」：答案含糊（"优化一下""弄好看点"）、自相矛盾、范围膨胀（"顺便把 Y 也做了"）、方案冒充需求（跳过问题直接给做法）、忽略已知环境硬约束 → **当场指出 + 给选项让 Doctor 收敛**，不附和。

**2d · 对齐收口（进起草的闸）**
阻断性歧义必须收口。三维够了或 Doctor 确认无疑问，CC 复述**对齐结论**：
```
对齐确认（请点头或纠正）：
- 核心需求（一句话）：…
- 开发方向 / 最小可交付：…
- 验收口径（硬标准几条）：…
- 非交付项（不做什么）：…
- 关键约束 / 红线：…
```
Doctor 确认 → 进 Step 3。**仍有阻断性歧义 → open_decisions 登记（事项/是否阻断/决策归属/状态），只就该分歧请 Doctor 裁定；非阻断问题继续。**

### Step 3 · 在场补采技术细节
基于任务需求，扫上下文把验收标准落到实处：功能/需求的主体结果是什么（→功能需求区）、有无性能/安全/可靠性/兼容性/数据质量要求（→非功能需求区）、会动哪些文件/目录（→§2.5 执行清单）、改完哪些旧名不该残留（→§2.5 `Grep = 0 matches`）、哪些产物要能跑通/打开（→功能验收方法）；读所属项目 `architecture/系统概览.md` + `GOTCHAS.md` 取项目专属红线 → 写进 §二C / §三。

### Step 4 · 复制模板填写
读 `~/Documents/Claude/brain/templates/prd-acceptance-template.md`，复制到
`~/Documents/Claude/brain/logs/checkpoints/{YYYY-MM-DD}_{任务简称}_PRD.md`。
填 §一（动机 + Doctor 原话 + 规模估算 + frontmatter 授权字段）、§二（A 功能需求 R* / B 非功能需求 N* / C 自定义 X*，**验收主体＝功能/需求、全可复核、全留 `[ ]`**）、§2.5（过程项 · 无 checkbox 表格）、§三（非交付项）。

### Step 5 · 自检（落盘前）
- `Grep` §二 是否混入主观词 → 改成可复核形式。
- 每条问"这描述的是一条用户可感知的结果或质量约束吗？能否用一行命令或预先定义的人工方法判定？"否 → 重写或移入 §2.5。
- §二/§三 是否忠实任务需求（没擅自加项 / 没漏 Doctor 在意的验收点）。
- 涉 git 则 §2.5 含"贴命令给 Doctor"（G-X2）。

### Step 6 · 回报（立卷完成）
```
📝 PRD 已立（功能/需求验收基线 · 任务已授权 → 我按 PRD 执行，不额外等 PRD 文本审批）
📁 logs/checkpoints/{YYYY-MM-DD}_{任务简称}_PRD.md
   核心需求：{一句话}
   交付标准：{N} 条（R*/N*/X* 全可复核，已留 [ ] 待执行时填三态）
   执行清单：{M} 项（§2.5 表格 task_status 跟踪）
   分轨（v1.3）：客观轨 {K} 条打包签总 ✓（审查员背书）· 原则轨 {J} 条逐条 ✓
   未决分歧 open_decisions：{L} 条（仅阻断性项列明请 Doctor 裁；非阻断项继续）
👉 执行完交验收：我逐条填 [?]+证据 → 独立审查背书 → Doctor/指定独立验收方打 ✓。
   注：✓ 只由 Doctor 或 Doctor 指定且未参与实施的独立验收方落，我全程不打 ✓、不自动关闭。
```

### Step 7 · 执行（任务已授权时直接实施）
按 PRD 执行，**每达成一条立即** `[ ]`→`[?]`+证据；达不到 `[!]`+原因；不确定 `[~]`。**仅在既有授权范围内实施**；范围扩大不私自加交付标准 → 请 Doctor 裁定。**部分阻断时保持 in_progress**（open_decisions 记阻断项），仅全部剩余需求被阻断才把顶层状态设 blocked。
执行中遇分叉裁定（方向/口径/处置方式需 Doctor 拍）→ **随时 AskUserQuestion，现行做法不变**；该裁定落 PRD 变更记录（Doctor 原话 + 时间），**不追加进原则轨**（原则轨只收开发后首现的验收裁定 · 2026-08-15 Doctor 立）。

### Step 7.5 · 独立审查（执行后、交验收前 · ★ 闭环）

CC 自审填完三态后，**派一个独立审查子 agent**对照 PRD 复核，再交验收方终审——形成三层闸：**CC 自审（填证据）→ 独立子 agent 审（对照标准）→ Doctor/指定独立验收方终审（打 ✓）**。

- **审查者人选**：优先 **句芒 `project-review`**（PRD对齐 + 代码/产物质量 + 精神洞察三层）；若句芒此时不是可运行子 agent，则起**一个干净的 Task subagent**——关键是它**未参与本次开发**（"另一颗干净的脑子"，借鉴视频"审查员没写过这代码所以审得准"）。
- **审什么**：逐条核 §二 交付标准——CC 填的 `[?]`+证据是否真成立（验收方法重跑 / 功能结果实测 / 人工验收记录核对）、有无完成幻觉漏项、产出质量。**只读不写产出物**（职责隔离换客观）。
- **背书（v1.3 分轨）**：审查通过后 CC 在 PRD §二「分轨签核」小节落**审查员背书记录**——审查者身份 + 验证动作记录（重跑命令 / 实跑输出摘录）。验收方抽查可复核；抽查发现背书失实 → 该场客观轨 ✓ **全部回退**。**审查员默认只有背书权，不自动取得 `[✓]` 权**（指定独立验收方由 Doctor 指定）。
- **闭环**：审不过 → CC 按审查意见改 → 复审，直到过；审过 → 才把 §四 current_status 改"awaiting_acceptance"，触发 /save 贴 PRD 路径，交 Doctor 或指定独立验收方终审。
- **分轨验收（v1.3 · 模板 §六 阶段 2.5）**：客观轨（机器可判事实）Doctor 或指定独立验收方签一个总 ✓；原则轨（结论/裁定类，通常 3-5 条且必须有真裁定含量）验收方逐条 ✓。CC 转录对话裁定落盘时注明原话与时间。
- **红线**：① 审查者必须是**未参与开发的干净上下文**，不得自审自过；② 审查者**也不打 ✓**——PRD 内 ✓ 只由 Doctor 或 Doctor 明确指定、且未参与实施的独立验收方落（实施者与审查者同属实施侧，不得验收自己的改动）；③ 审查意见与 CC 分歧时如实呈给 Doctor，不替 Doctor 拍板。

## §5 · 对齐问题库（参考 · 三维 × 要问/算清/打回）

> 这是 what 不是 how，可写厚（遵 [[skill写作规范]]）。**条件触发**：仅在发现需求模糊/信息不足/范围冲突/验收标准无法落成时启用，按维度取用、不必逐条问；Doctor 原始指令已说清时跳过本节。

### 维度一 · 核心需求（要解决什么、为谁、为什么现在）
- **要问**：这次到底要解决什么问题？为谁？成功长什么样（一句话可感知）？不做会怎样（定优先级）？
- **算清**：能用一句话说出"痛点 + 谁受益 + 可感知的成功态"。
- **打回信号**：目标含糊（"优化/弄好看/完善一下"）；能解释任意结果的万能目标；**把方案当需求**（直接说"做个 X"却说不出 X 要解决的问题）。

### 维度二 · 开发方向 / 形态（范围、做法、约束）
- **要问**：范围多大？**最小可交付**是什么？有几种做法、各 trade-off、倾向哪种？改存量还是新建、波及哪些已有文件/项目？环境/数据/红线约束（Cowork 沙箱 / 数据真实性铁律 / G-X 硬坑）？
- **算清**：MVP 边界清晰 + 选定一个方向（大方向由 Doctor 拍，CC 给选项与 trade-off）+ 列明约束。
- **打回信号**：范围无边界；"顺便把 Y 也做了"（膨胀）；方案与问题不匹配；无视已知环境硬约束。

### 维度三 · 交付与验收（怎么算完、怎么验、不做什么）
- **要问**：怎么算做完？哪几条是**硬验收**？每条怎么验（机器比对 / 人工验收方法 / Doctor 测）？明确**不做**什么？谁验收（Doctor 或 Doctor 指定且未参与实施的独立验收方）、何时验？
- **算清**：每条验收主体＝功能/需求（可复核口径）+ 划定非交付项。
- **打回信号**：验收主观（"做好了就行"）；没有可复核口径；没划非交付项（范围必漂）。

## §6 · 与既有机制联动
- **G-X4 / prd-acceptance-template**：本 skill 是 G-X4 的"对齐器 + 立卷器"，治理铁律全继承模板 §六/§七/§八；PRD 立卷不新增审批门（任务授权与方向判断遵循既有授权边界）。
- **句芒 project-review / Task subagent**：Step 7.5 独立审查的执行者（数灵转移设计 §九.2 审查者归句芒）——**审查员默认只有背书权**，不自动取得 `[✓]` 权。
- **AskUserQuestion**：Step 2b 条件对齐（选择题）与 Step 7 分叉裁定的主力工具。
- **brain-save**：执行结束 /save 贴 PRD 路径 + 状态（brain-save Step 6）。
- **TaskList**：PRD 管"什么算 done"，TaskList 管"怎么做"，并行不冲突。
- **未来可拆**：若对齐问题库长到独立成势，可分出 `brain-spec`（需求对齐）+ brain-prd（立卷）两 skill；当前合一够用。

## §7 · 边界
- 模板缺失 → 用 G-X4 §四结构 fallback，仍守三态 + 不打 ✓。
- 任务很清晰（Doctor 已把需求/验收说全）→ **跳过对齐直接立卷**，不强行多轮。
- 任务中途缩成小改 → 可撤 PRD（只 Doctor 决定）。
- checkpoints/ 不存在 → 先建。
