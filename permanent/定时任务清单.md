- **任务文件**：`~/Claude's workspace/Scheduled/{taskId}/SKILL.md`（**注意路径带空格与撇号**）。
  - **★ 读写边界（2026-08-01 实测订正 · 本条原写「沙箱挂不了，只能 Doctor 终端 cat 出来」，那只说对了一半）**：

    | 通道 | 对 live 树 | 实测 |
    |---|---|---|
    | `Read` / `Grep` / `Glob`（宿主机侧工具） | **✅ 读得到** | 直接读出 `us-close-backfill/SKILL.md` 全文并 `grep` 计数 |
    | `Write` / `Edit` | **❌ 封死** | 报 `outside this session's connected folders` |
    | `mcp__workspace__bash`（沙箱） | ❌ 够不到 | 沙箱只挂 `~/Documents`，`~/Claude's workspace/` 不在挂载表里 |
    | `request_cowork_directory` 补挂 | ❌ 会被直接拒 | 管理员限定 allowed roots **只有 `/Users/lunarabbit/Documents`**，域外请求不弹窗、静默拒绝 |

  - ⇒ **「CC 无法维护任何 live 定时班」这个说法要收窄为「写侧封死」**。**读侧是通的，且这个收益是实的**：改 SKILL 前 CC 可**自己取 live 全文**做核对与 diff，不必劳 Doctor `cat` 贴过来；装完也可自己 `grep` 核内容标识。**只有安装那一步（`cp` 覆盖）仍必须 Doctor 终端做。**
  - 写入路径不变：CC 备好完整文件落 `~/Documents/Claude/_merge-staging-YYYYMMDD/` → Doctor 终端先 `.bak_YYYYMMDD` 再 `cp` 覆盖 → **收尾必跑 `diff` 确认逐字一致**（内容标识 `grep -c` 只作辅助，且**期望值必须先实核**，见 [[通用教训]] G-X120）。或用 `create_scheduled_task` 写。
- **⛔ 存在第二棵同名树：`~/Documents/Claude/Scheduled/`（2026-07-31 查明 · 本条此前写的就是这个错路径）**。它是**真实目录、非软链**（`readlink -f` 两边不同），沙箱**能**读写，但**调度器根本不读它**。实测：live 20 个班 / 该树 14 个，仅 live 有 8 个班、仅该树有 0 个；两棵树里 6 个班内容不同。
  - **后果实例**：2026-07-30 深夜给 `zhuzhao`（加 5f 终检步）与 `recap-kejian-review`（标 `--phase=ingest-check`）改的 SKILL **全部落在这棵死树上**，无任何报错、文件确实改了，但**从未进过生产**；`baize-weekly-report` 的 07-09 改动更是搁了 22 天。详见 [[通用教训]] **G-X118（静默成功）** 与 [[经验库]] **EXP-20260731-006-T**。
  - **本条就是病根**：原文把**路径**取自 Documents 树、把**属性**（受保护/沙箱挂不了）取自 workspace 树，两棵混成一条。照着它去改 SKILL，必然改到死树上。
  - **认哪棵是活的**：`list_scheduled_tasks` 每个任务返回的 `path` 字段直指被消费的那份，**这是唯一权威来源**——别靠目录名、mtime 或"哪个看起来新"猜（实测两棵树同一晚都被动过，时间戳会骗人）。判死活用「拿一件已知的具体改动去两处 `grep`」。
  - **处置**：Documents 那棵待三份分叉 SKILL 合并完后改名 `_DEPRECATED_Scheduled_YYYYMMDD/` 归档（**改名不删**）。在那之前，**任何 SKILL 改动一律直接改 live 树**。
- **`SKILL.md` 的 frontmatter 只有 `name` + `description`**——**调度信息（cron/每天几点）不在文件里**，写在 description 的散文里给人看。真正的 `cronExpression` / `enabled` / `nextRunAt` 存在一张**独立的注册表**。
- ⚠️ **故"光有 SKILL.md 文件 ≠ 任务已注册"**：切环境后旧文件还在 `Scheduled/` 里，但新环境注册表是空的 → `list` 返回 0。**必须用 `create_scheduled_task` 重建**（它把 prompt 正文 + cron 一起登记），不能只靠拷文件。
- **jitterSeconds（确定性延迟）**：平台在调度时刻给每个任务加几分钟随机偏移分散负载（如设 06:15 实跑 06:20、06:30→06:38）。**正常**，只要任务间相对顺序不乱即可。
- **cron 用 user 本地时区（中国 UTC+8）**，不是 UTC，直接写本地时间。
- **cron 的 `,` 列表（如 `3,6`）有效**，但人类可读摘要可能渲染不全（实测 `30 8 * * 3,6` 摘要显示「only on Wednesday」漏了周六，**底层 cron 是对的、照常周三+周六跑**）——以 `list_scheduled_tasks` 返回的 `cronExpression` 字段为准，别信摘要那行。

## 路径解析：gateway 平铺挂载 → 脚本 env 覆盖（G-X45 · 两批全完 2026-07-01）

gateway 把请求挂载的目录平铺到 `mnt/{basename}`，不还原 macOS 层级——脚本靠 `parents[N]`/向上找 `Documents` 定位兄弟目录（输出区/库/AI4ME）会算错。解法：脚本加 env 后门（有 env 用 env、无则回退老逻辑，Mac 原生零影响），任务 prompt 补「前置：挂载 + 路径 env」块导出之。

| 任务 | 脚本 | env 变量 |
|------|------|----------|
| zhuzhao-…-daily-report | `gen_daily_report.py` / `market_health.py` | `ZZJY_OUTPUT_ROOT` · `ZZJY_ARTIFACT_ROOT` · `ZZJY_DATABASE_ROOT` · `MARKET_DATA_DIR` |
| baize-weekly-report | `build_weekly_report.py` · `sync_to_cowork_artifact.py` · `weekly_health.py`（+ `lib_public_read`/`lib_paths`） | `BAIZE_OUTPUT_ROOT`(AI4ME) · `BAIZE_DATABASE_ROOT`(Database·龙鱼库) · `BAIZE_ARTIFACT_ROOT`(Artifacts)；`BAIZE_BUSINESS_DB` 更具体优先 |
| refresh-asset-dashboard | `conch_engine.py` | `CONCH_DOCUMENTS_ROOT`(survey 解析各项目相对路径的 Documents 根) |

第一批（烛照/行情线）2026-06-30、第二批（白泽/海螺周更线）2026-07-01。详见 [[通用教训]] G-X45。
