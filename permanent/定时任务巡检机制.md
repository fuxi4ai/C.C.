# 定时任务巡检机制

> **一句话**：把「定时任务现状」从**靠记忆和日志拼**，改成**一条命令拉**；把「谁改了什么」交给 `git diff`，不再需要任何人记得。

---

## 一 · 为什么要有它（病根，不是需求）

2026-08-01 一天之内，CC 关于定时任务的结论**被推翻三次**：

| CC 说的 | 实际 | CC 的信息来自 |
|---|---|---|
| 「backfill 周一 13:34 验四失败面」 | 班已改 **14:30** 且**不再写库**（08-01 09:00 重构为只读看门狗） | 08-01 凌晨的日志 |
| 「双写者职责未理清」 | zhuzhao 当天已加**单写者锁** | 07-31 的日志 |
| 「launchd 有 2 个 job」 | **3 个**，第三个（`com.zhuzhao.usclose`）不在任何清单里 | 08-01 凌晨的清单 |

**三条都有出处、都自洽** —— 因为它们都是从**日志**拼出来的，而日志是历史。只要中间有一场 CC 没参与的会话动过 live 树，拼出来的图就是错的，**而且看不出错**。

**这与 2026-07-31 挖出的「Documents 死树」是同一个病的两面**：

- 死树 ＝ **记了但没人读**（改动落进真实存在、却没人读的位置）
- 本病 ＝ **读了，但读到的不是现在**

⇒ **根治方向不是让人记得更牢，而是让「现状」可被一条命令拉出来。**

## 二 · 怎么跑

```bash
python3 ~/Documents/Claude/brain/.tools/scheduler_snapshot.py
```

**必须在 Mac 原生跑** —— 沙箱只挂 `~/Documents`，读不到 `~/Claude's workspace/`（live 树）与 `~/Library/LaunchAgents/`（launchd 装机位）。

输出两份**固定文件名**：

| 文件 | 给谁看 |
|---|---|
| `brain/permanent/_scheduler_snapshot.json` | 机器 / `git diff` |
| `brain/permanent/_scheduler_snapshot.md` | 人 |

**只读保证**：除自己这两个输出外不写任何东西；不跑 git 子命令；`launchctl print` 与 `crontab -l` 都是只读查询。

## 三 · 查什么

> **⚠ 覆盖边界（2026-08-02 订正 · 先读这条）**
>
> 下面这「四个执行面」**只覆盖 Doctor 的 Mac**。已知**至少还有第五个**：
> **DVA 的 fuxi Windows 侧**（`E:\AI\DVA\ops\` —— refill / 采集 / 分析 / 轮巡健康告警，
> 有独立的 failure / log / summaries 目录与自己的告警节奏）。**本脚本完全够不到它**（跨机器）。
>
> **为什么必须写在最前面**：一个声称覆盖全面的巡检机制，若自己有未声明的盲区，
> **比没有机制更危险** —— 它会让人以为已经查过了。这与本机制要消灭的病（静默缺失）是同一个。
> 初稿写「四执行面」而未声明边界，口气像是穷尽，是一处过度自信的表述。
>
> 跨机器纳入是另一场（脚本跑不到 Windows，得另想办法）。**在那之前，凡引用本机制说
> 「定时任务都查过了」，一律要补一句「Mac 侧」。**

### 四个执行面（均在 Mac）

| 面 | 位置 | 记什么 |
|---|---|---|
| ① Cowork live 树 | `~/Claude's workspace/Scheduled/` | 每班的 SKILL **mtime / 行数 / sha12 / name / description** |
| ② Documents 死树 | `~/Documents/Claude/Scheduled/` | 目录数 · 与 live 同名者 · **仅死树有** · **内容分叉** |
| ③ launchd | `ops/*.plist`（源）↔ `~/Library/LaunchAgents/`（装机） | 排期 · 入口程序 · **源↔装机 sha 一致性** · `launchctl` 实际加载态与 last exit code |
| ④ crontab | `crontab -l` | 是否真为空 |

### 三类一致性（这才是它的价值所在）

普通清单只记「有什么」，本机制记「**两处该一致的地方是不是真一致**」：

1. **死树 ↔ live 内容分叉** —— 改了看起来生效、实则没进调度器（07-31 ERR 的原型）
2. **plist 源 ↔ 装机位 sha** —— **改了源没重装 ＝ 死树分叉的 launchd 版**
3. **装机 ↔ 实际加载**（`launchctl print`）—— 装了文件 ≠ 已加载

## 四 · 怎么用：`git diff` 就是变更检测器

输出用**固定文件名**且**纳入 git**，于是「谁改了什么」不需要任何额外机制：

```bash
python3 ~/Documents/Claude/brain/.tools/scheduler_snapshot.py
cd ~/Documents/Claude/brain && git diff permanent/_scheduler_snapshot.json
```

**diff 里出现的每一行，都是自上次快照以来真实发生的变化** —— 无论改动来自 Doctor、别的 CC 会话，还是本人。

> **系统不需要知道是谁改的，只需要能发现变了。** 这一条绕开了「多会话并发改同一资产、事后无人说得清」这个死结。

⚠️ **第一次跑时 diff 是空的**（文件还 untracked，无基线可比）—— 必须先 commit 建立基线。基线已于 2026-08-02 建立（commit `e13f414`）。

## 五 · 覆盖不到的（显式缺口，不是静默缺失）

写在输出的 `_gaps` 字段里：

1. **Cowork 班的 cron 表达式** —— 只有 `list_scheduled_tasks` 这个 MCP 工具给得了，脚本拿不到。快照里 `cron` 恒为 `null`，**由 CC 调工具回填**。勿把 `null` 当成「没有 cron」。
2. **`notifyOnCompletion`** —— 同理，`list_scheduled_tasks` 不返回（2026-07-30 实测）。但 **`update_scheduled_task` 可以设**：读不到 ≠ 设不了。

**这两条是显式声明的**，因为「静默的缺失」正是这套机制要消灭的东西 —— 自己不能犯同样的病。

3. **新鲜度判据的盲区（2026-08-02 实测补记）** —— `/resume` Step 0.6 与第一层自证都以快照 `generated_at` 新旧为判据，但**新鲜度区分不了「谁写的」**——手动会话跑一次脚本，快照就新了。两个方向都会骗人：① 手动跑完，次日 resume 报 ✅，被读成「周班在跑」（假绿灯）；② 反过来把「快照是手动写的」推成「周班停摆」同样错（08-02 两个方向各错一次，后者见 [[通用教训#G-X119]] 追记）。**根治候选（未做）**：快照 `_meta` 加 `triggered_by` 字段（scheduled/manual），脚本侧一行改动；在此之前，判「周班活着没有」以 `list_scheduled_tasks` 的 `lastRunAt` 为准，快照新鲜度只判「巡检这件事最近发生过没有」。

## 六 · 与 `定时任务清单.md` 的分工（提议，待 Doctor 定）

清单现在同时装着两类保质期完全不同的东西：

| 类别 | 例子 | 保质期 |
|---|---|---|
| **会变的** | 班数、cron 钟点、SKILL mtime、launchd 几个 job、死树几个目录 | **天** |
| **不变的** | 为什么 usclose 排在 marketdata 之后（收盘后 1h vs 开盘前）· 为什么写库必须 Mac 原生（G019 + FDA 授权主体是顶层程序）· 为什么体检要挪到末位写库方跑 · 五表双写的权属问题 | **月** |

⇒ **「会变的」交给快照，清单只留「不变的」**，变成一份**解释性文档**（讲架构、依赖次序、每条铁律的来由）。

这样清单**不再会过期**，因为它不再记会变的东西 —— 而 08-01 那三次推翻，**全部发生在「会变的」那一类上**。

代价：清单要大改一轮（现 192 行里大半是会变的数字表），且两边引用要理顺。**未执行。**

## 八 · 输出契约：正常时一个字都不打印（2026-08-02 补）

**巡检必然退化。** 跑一个月后所有人都会习惯性略过那几行摘要 —— 这与 `G-X119` 记的「两问的答案总是『核过了、没隐患』就是它变成套话的信号」是同一回事。

⇒ **解药只有一个：正常时不出声。**

| 模式 | 行为 |
|---|---|
| 默认 | **无异常 → 零输出，exit 0**；有异常 → 清单写 stderr，**exit 1** |
| `-a` | 连 🟡 级也报（exit code 不变） |
| `-v` | 打印四面全摘要（人工排查用） |

### 什么算异常（刻意保守，宁可少报也不误报）

**🔴 必须出声**

- Cowork live 树读不到
- 某班没有 `SKILL.md`
- **班消失了**（对比上次快照；新增不报，那是正常操作）
- launchd 自有 job：**未加载** / **上次退出码非 0** / **源↔装机不一致**
- **仅死树有**的班 —— 这些改动从未进过调度器

**🟡 默认不出声**（`-a` 才报）

- 死树内容分叉 —— **已知且已判定无害**（live 均较新、无死树独有）。若列 RED 它每次都响，那是把巡检训练成背景音的最快方式
- crontab 非空 —— 第四执行面启用需入账，但不紧急

**第三方 launchd（Google Updater / 网盘等）一律不报** —— 不是我们的，混进来只会淹没真信号。

### 分工：脚本报「破损」，git 报「变化」

**变化本身不算异常**。每次改个班脚本都喊一嗓子，两周内必被无视。⇒ 变化交给 `git diff`，脚本只报**结构性破损**，两者不重叠。

**唯一的例外是「班消失」**：`git diff` 虽也能看见，但**没人会盯着 diff 找减号**，而误删的代价不对等。故这一条脚本自己出声。

## 九 · 定期化：周班设计与那个悖论

### 悖论

> **巡检定时任务的东西，自己也是个定时任务。它坏了谁发现？**

一个只依赖自己的巡检器，停摆时是完全静默的 —— 这恰恰是它要消灭的病。

### 解法：两层，缺一不可

**第一层 · 巡检班自证**：脚本读上次快照的 `generated_at`，**若距今 > 8 天则报 🔴「巡检中断过 N 天」**。班每周跑，正常间隔 7 天；一旦漏跑，下次跑时自己就把这个事实喊出来。

**第二层 · `/resume` 兜底**：第一层挡不住「永远停摆」——没有下一次跑，就没有人报。故 `brain-resume` 需加一条：**检查 `_scheduler_snapshot.json` 的新鲜度，超期即提示**。这样每次 Doctor 开工都是一个检查点，不依赖任何定时机制。

⇒ **定时的东西用不定时的东西兜底**，这是唯一能跳出悖论的结构。

### 周班形态（待建）

| | |
|---|---|
| 排期 | 周日（避开工作日；与 `agents-memory-meditation` 09:05、`baize-weekly-report` 01:00 错开） |
| 动作 | 跑脚本 → 读退出码 |
| exit 0 | **静默**。不通知、不 commit（避免每周一个只有时间戳变的空 commit 污染 git 历史） |
| exit 1 | 通知 Doctor，附 stderr 的异常清单 ＋ `_scheduler_snapshot.md` 路径 |
| 不做 | 不自动修、不自动 commit、不碰调度器 —— 巡检器一旦获得写权限，它自己就成了需要被巡检的东西 |

**为什么 exit 0 时不 commit**：每周一个空 commit 会让 `git log` 变噪声，而 git 的价值恰恰在于「有 diff ＝ 真变了」。班跑没跑改由**快照文件自身的 mtime** 证明（第一层已覆盖）。

**⚠ 未建**。建之前必须先在真机验证三种模式（默认静默 / `-a` / `-v`）行为正确 —— 否则班会每周失败一次，而失败的是巡检器本身，最不该。
