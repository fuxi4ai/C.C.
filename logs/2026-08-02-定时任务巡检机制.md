## 三 · 装出来的东西

### 3.1 快照脚本 `brain/.tools/scheduler_snapshot.py`

**四个执行面** ＋ **三类一致性**（后者才是价值所在 —— 普通清单只记「有什么」，它记「两处该一致的地方是不是真一致」）：

1. 死树 ↔ live **内容分叉**（改了看起来生效、实则没进调度器）
2. plist **源 ↔ 装机位** sha（改了源没重装 ＝ 死树分叉的 launchd 版）
3. 装机 ↔ **实际加载**（`launchctl print`；装了文件 ≠ 已加载）

**只读**：除自己两个输出外零写入、不跑 git 子命令、`launchctl print` / `crontab -l` 均只读。

### 3.2 `git diff` 当变更检测器

输出**固定文件名**并纳入 git ⇒ **「谁改了什么」不需要任何额外机制**。这一条正面绕开了「多会话并发改同一资产、事后无人说得清」这个死结 —— **系统不需要知道是谁，只需要能发现变了。**

### 3.3 输出契约：正常时一个字都不打印

> 巡检必然退化。跑一个月后所有人都会略过那几行摘要 —— 同 G-X119「两问的答案总是『没问题』就是它变套话的信号」。

⇒ 无异常 **零输出 exit 0** · 有 🔴 写 stderr **exit 1** · `-a` 连 🟡 也报（**不改退出码**）· `-v` 全摘要。
**变化不算异常**（交给 git diff），脚本只报**结构性破损**，两者不重叠。**唯一例外是「班消失」**：没人会盯着 diff 找减号，而误删代价不对等。

### 3.4 周班 `scheduler-weekly-audit` 与那个悖论

**悖论**：巡检定时任务的东西自己也是定时任务，它坏了谁发现？

**两层解法，缺一不可**：

- **第一层 · 自证**：脚本读上次快照 `generated_at`，>8 天报 🔴「巡检中断过 N 天」。漏跑一次，下次跑时自己喊。
- **第二层 · `/resume` 兜底**（`brain-resume` Step 0.6，已存进 Doctor 账号）：第一层挡不住「永远停摆」—— 没有下一次跑就没人报。

⇒ **定时的东西必须用不定时的东西兜底**，这是唯一能跳出悖论的结构。

班的形态：周日 20:00 PDT（＝北京周一 11:00）· `notifyOnCompletion=false`（否则每周一条「跑完了」毁掉静默）· **exit 1 时发 macOS 系统通知**（这是异常唯一的送达路径）· **不自动修、不 commit、不碰调度器**（巡检器一旦有写权限，它自己就成了需要被巡检的东西）。

## 九 · 本场方法论

### 「谁改的」不重要，「变了没有」才重要

多会话并发改同一资产，事后追责是死结。但**换个问法就解开了**：不问「谁改的」，只问「和上次比变了什么」。固定文件名 + git，一条 `diff` 就够 —— 不需要任何人记得，也不需要任何额外机制。

### 告警的价值由它沉默的时候保证

正常时说「一切正常」，等于每周花掉一点信任额度，两周就透支完。**零输出不是省事，是让异常那一句还有人信的唯一办法。** 同理，一条 RED 误报的破坏力远大于漏报一次 —— 漏报只是这次没发现，**误报会训练人忽略 RED**。

### 装工具的人最容易在工具上犯自己刚记下的错

今晚四次自栽，每一次都对应今天早些时候刚写下的教训（G-X111 / G-X120 / 「文档≠代码」）。**写下一条教训与遵守它之间，隔着的不是理解，是一次具体的检查动作。** 而那个动作至今没有形态 —— 这是比任何单条教训都更值得想的事。

Doctor 通报：补跑结束 RECOVERED，`DVA-Refill` **返回 0**、锁已释放；但**本次 refill 终态为 FAILURE / exit_code 1**，采集 8/8 成功、**内嵌金融分析失败**；随后精确修复成功发布 2/2 位作者、待修登记清空、轮巡恢复日常。

**⇒ 「跑完了」≠「产生了效果」在 DVA 线上的同款**：外层留的痕是 0，内层的真相是 1。**任何只看外层退出码的监控都会判成成功。** 若两层语义是刻意分层（外层＝补跑流程完成、内层＝业务结果），那不是 bug —— 但**必须有一层显式把内层状态抬到外层能看见的地方**，否则下次没人贴过来，它就是静默的。

⚠ 三个文件（failure / log / 修复摘要）都在 `E:\AI\DVA\ops\`，**沙箱读不到**，本条只能按 Doctor 描述记，缺细节。

### ② Mac 快照追平 fuxi —— 一个正面样本

`2026-08-02 14:26:20 UTC` 刷新。**我实核了报告**（文件在 `~/Documents/Database/Douyin/`，沙箱够得到）：

```
bundle_sha            ok
reconcile   18,347 files / 6,266,776,319 bytes   ok
sqlite      integrity ok · offsite_cols ok · offsite_rows 1434
json_db     authors 12 · video_records 1292
pre_refresh_kept  5 个目录全留（可回滚）
ok: True
```

**这次验证是四层，第四层才是关键**：① bundle SHA-256（传输完整）② 逐文件对账（内容完整）③ SQLite `integrity_check`（结构完整）④ **`offsite_cols`/`offsite_rows`/`authors`/`video_records`（业务语义对得上）**。前三层只证明「东西都到了」，**第四层才证明「到的是对的东西」**。

且 `ok: True` 是所有子步骤 ok 之后的**合成结论，每个子步骤的原始值都留在报告里** —— **合成了结论，但没吞掉证据**。

**与 ① 恰成对照**：同一条 DVA 线上，一边是「分了层却没把内层抬上来」，一边是「逐层验、逐层留痕、最后才合成」。后者是对的做法。

**连带**：`offsite_rows = 1434` —— 07-31 结案的「三个 Mac 库行数互不包含（1396 / 1434 / 1559）」中，fuxi 那条线已追平到 Mac。那条 TODO 的**前提部分变了**，但结案判断（dyd 库是 Mac 单链保底线的真相源、不该指向任何归档库）不受影响。

今晚盘的四个面（Cowork live 树 / Documents 死树 / launchd / crontab）**全在 Mac 上**。`E:\AI\DVA\ops\` 这条线跑在 **fuxi 的 Windows** 上，有自己的轮巡与告警 —— **完全在快照脚本的视野之外**。
