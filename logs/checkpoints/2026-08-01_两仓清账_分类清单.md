## 三 · 本次盘点顺带挖出的两个真问题

### 1 · `兑现变更_` 命名分裂成两种格式，且**新格式是错的那一种**

untracked 的 9 件里，两种命名各半：

- `兑现变更_2026-07-22.md`、`_2026-07-24`、`_2026-07-26`、`_2026-07-27`、`_2026-07-29`、`_2026-07-30`（**带横杠**）
- `兑现变更_20260723.md`、`_20260728`、`_20260731`（**不带横杠**）

而**已 tracked 的 19 件全部不带横杠**（`20260625` … `20260721`）⇒ 不带横杠是既定惯例，带横杠的 6 件是漂移。

**成因已核**：全仓 grep `兑现变更_` 在 `.py`/`.sh` 里**零命中** ⇒ 这批文件**不是脚本生成的，是会话里手写落盘的**，所以命名全靠当次记得。这与 escalation_shadow 形成对照——后者有 `tools/escalation_shadow.py` 生成，命名 9 件全一致、零漂移。

**⇒ 这是 G-X103「靠人记得的机制不可靠」在文件命名上的又一个实例。** 内容格式也跟着分裂：`2026-07-22` 那件只有 155 字节（「共 0 条状态变更」），而 `20260723` 是 1847 字节的完整 diff 记录。

**未定**：改名统一 vs 原样入仓。改名会让「已发生的历史」看起来整齐，但那不是当时的真相；不改则仓里永久留下两种格式。**倾向原样入仓 + 往后由脚本接管命名**，但这需要您定。

### 2 · 烛照九阴仓上次 commit 停在 07-21（日更文档口径）

四族日更文档 tracked 的最后一天全部是 **07-21**，此后 10 天全在工作树里。而仓库整体 08-01 00:35 还在 commit（launchd/guarantee_ratio 那批）⇒ **不是「没人提交」，是「提交时从没带上 docs/ 日更产物」**。每次 commit 都是围绕当次改动精准 add 的，日更产物永远不在当次改动范围内，于是永远漏。

**⇒ 这类文件需要一个独立的提交节奏（或让生成脚本提交），否则会一直积。** 不解决这一条，今天清完，10 天后原样复现。

## 五 · 本清单的失败模式（G-X119 · 主动列）

1. **`.gitignore` 匹配是我自己实现的，不是 git 的**。我用 `fnmatch` 近似了 gitignore 语法，**未实现否定规则 `!`、未实现 `**` 中段匹配、未实现目录锚定 `/` 前缀的完整语义**。两仓现有规则都很简单（无 `!` 规则），本次风险低，但**若某个文件其实被 git 忽略而我列成了 untracked，就会诱导您提交一个本不该进仓的文件**。校验法：您那边跑一次 `git status --short` 与本清单对表，数字应为 17/2 与 51/1。
2. ~~`assume-unchanged` / `skip-worktree` 会让 modified 判据失效~~ → **已核销**：实扫两仓 index 全部 1486 条 entry，`assume-valid` **0**、`skip-worktree` **0**。
3. ~~`.gitattributes` 若定义 filter（如 LFS），SHA 比对会全线误判~~ → **已核销**：两仓**均无** `.gitattributes`。
4. **B 档「同族 tracked 数＝0 所以不该入仓」是从惯例推的，不是从意图推的**。惯例可能本身就是疏漏——`_ingest_九儿_*` 被 GOTCHAS 正式点名却无版本记录，恰恰暗示惯例这次可能是错的。已在 B 档正文标出，但**判断权在您**。
5. ~~未核带横杠 6 件的内容是否随格式退化~~ → **已逐件核**：6 件字节数 155 / 2195 / 1208 / 991 / 2116 / 4614。**内容无退化**——最小那件（`2026-07-22`，155 字节）正文是「共 0 条状态变更」，那天本就无变更，短是对的。
   **但补一个新发现**：标题也分裂成三种——「兑现变更」/「兑现状态变更」/「兑现状态变更留痕」，跨两种文件名格式交叉出现。⇒ 漂移在**文件名与标题两层**，进一步坐实「手写、无脚本约束」这一成因。
