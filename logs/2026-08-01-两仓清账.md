### 一 · 绕开 G-X97 读仓况 —— 用 python 直读 `.git/index`，零 git 子命令

**约束**：全局硬约束禁在沙箱跑**任何** git 子命令（含 `status`——会留 `index.lock` 且沙箱无权删）。而 untracked / modified 恰恰**无法从 `.git/` 的纯文本文件得出**：untracked 要比对工作树与 index，modified 要比对内容，而 `.git/index` 是二进制。

**做法**：写 python 解析 index v2 格式（12 字节头 `DIRC` + 每条 62 字节定长 + 变长路径 + 8 字节对齐），拿到 tracked 集合；再
- **untracked** ＝ 工作树遍历 − index 路径 − gitignore 匹配
- **modified** ＝ 逐文件重算 `sha1("blob {len}\0" + content)` 与 index 里的 SHA 比对（**比 mtime 准**，不受 racy-git 影响）
- **改动规模** ＝ 从 `.git/objects/{2}/{38}` zlib 解出旧 blob，与工作树做 `difflib` 计行

**⇒ 「不能跑 git」不等于「读不到仓况」。** 约束限的是命令，不是信息。这套方法在沙箱里完整复现了 `git status` 的三类输出，且**不产生任何 `.git/` 写入**。

### 五 · ★ 判据维度盲区 —— 本场自己栽的那一个

Doctor 第一次跑命令块时从 heredoc 中间断裂重跑，导致 `.gitignore` 那 8 行**被追加了第二遍**。而我给的验收判据是 `git status --short | wc -l`，期望 brain `1` / 烛照九阴 `0`——**两个数字都对上了**。

**因为重复的 ignore 规则恰恰是 `git status` 永远看不见的那种错。** 真正暴露它的是 commit 回显里那句 `1 file changed, 8 insertions(+)`——一条我差点当噪声放过的行，它出现在一片"验收全绿"里。

**⇒ G-X120 的未覆盖面**：那条讲的是**期望值算错**（凭印象敲 `1/1/1/0`）。本次期望值是实核的、也确实对上了，**错的是判据的维度**——我选的尺子看不见这次改动特有的失败形态。

**订正后的做法**：设计判据时先问「**这次改动会怎么坏**」，再选一个**能看见那种坏**的尺子；而不是选一个通用的健康指标。本次正确的判据应是 `grep -c` 三条规则各自出现次数（期望各 1），那是重复追加唯一会显形的地方。

**顺带一条更小但更实用的**：`cat >> file <<'EOF'` **天然不幂等**，而给 Doctor 的多段命令块**必须假设会被分段或重复粘贴**。去重那一版我改用 `head -31 file > tmp && mv tmp file`——重跑一次结果相同。**给别人跑的命令，幂等性是一项设计要求，不是巧合。**

## 本场方法论

### 约束限的是命令，不是信息

「不能跑 git」被我（和以往的会话）默认理解成「读不到仓况」，于是仓况只能靠 Doctor `cat` 贴过来。实际上 index 是有公开格式的二进制，objects 是 zlib，refs 是明文——**整个 `.git/` 都是可读的数据结构，git 只是它的一个前端。** 碰到硬约束时，先分清它限的是**动作**还是**目标**；限动作的，往往还有别的路。

同族：上一场刚订正过 live 树「读侧通、写侧封死」——也是把一个笼统的「够不到」拆成了两半。

### 判据要能看见「本次改动」的失败形态，不是任意失败

G-X120 管的是判据的**期望值**算没算过；本场发现还得管判据的**维度**选没选对。`git status` 是一把好尺子，但它量不出「同一条 ignore 规则写了两遍」——而那正是本次改动唯一会坏的方式。

**设计判据的顺序应该反过来**：先列「这次改动会怎么坏」，再挑能看见那种坏的观测点。从「有什么通用健康指标」出发，必然漏掉改动特有的失败面。

### 给别人跑的命令，幂等性是设计要求

`cat >> <<EOF` 不幂等，而多段命令块**一定会**被分段粘贴、断裂重跑——这不是意外，是使用方式。同样一件事，`head -N > tmp && mv` 就是幂等的。**写命令时假设它只会被完整执行一次，是一个已被证伪的假设。**
